# Session 2026-08-25 — task boards, and emailing the view you're looking at

**Machine:** desktop. **Migrations:** none written. **Commits:** `a7c5181`,
`d6766ac`, `4526d2b`. Dashboard-only; no prod data touched.

## The arc

Set out to do one thing: make the event hub's Tasks tab look like the calendar's
task list. Ended up doing three, and the second and third were both found rather
than planned.

**Built it, then watched it fail for a reason that wasn't the code.** The board
was finished, tested and syntax-checked — and Keith reported it "not right",
describing the *old* UI. It had never been deployed. It was held back
deliberately (master auto-deploys, and the work wasn't green-lit), which was a
defensible call made invisible to the person looking at the screen. The lesson
isn't "always push" — it's that "done" and "visible to Keith" are different
states, and only one of them is what he asked for. Say which one you're in.

**The filters exposed three bugs that could not exist before them.** A board with
no filters has no stale filter state, no rows that should leave when their status
changes, and no search box to lose focus in. Adding the feature created all
three, and the third (one character per click in the search box) had been sitting
in the calendar board unreported — nobody had used the search.

**Then the close found the real one.** Prod is on migration **203**; the repo
stops at **202**. `203_plan_line_quantity.sql` was applied from the laptop on
2026-08-22 and never committed — not in the tree, not on a branch, not in any
commit. Recovered its effect by introspection (`plan_offering_lines.quantity
numeric default 1 NOT NULL`) but deliberately did **not** author a replacement:
a different `sha256` from the one in `applied_migrations` would make the drift
permanent and invisible instead of temporary and loud.

## Key decisions

- **§50 — a filtered view sent onward must say what it filtered out.** Emailing
  the current view is right, but the recipient can't see your filter chips. Four
  tasks sent under "high priority · overdue only" reads as "four things
  outstanding". The filter now rides in the subject, a scope line and an *N of M*
  note; an unfiltered send carries none of it, so silence is information.
- **Deleted a control rather than reconciling it.** The hub mail's "Include
  completed tasks" checkbox could disagree with the board's `done` chip. Two
  controls for one decision is a way to send a list that doesn't match the screen.
- **Shared, not copied.** One `buildTasksEmailHtml`, one set of filter-wording
  helpers. The two boards were one paste away from describing the same state in
  two different sentences.
- **`data-ht-*` not `data-tb-*`.** Both boards can be in the DOM; a shared
  attribute fires the wrong re-render.
- **Left `hubAssignTask` in place, unwired, with a note.** `openEditTask` covers
  assignment but its assignee list is narrower (no venue contacts). Deleting it
  would have been a silent capability loss; leaving it silent would have been
  drift. Neither — so, a comment saying which.

## The honest note

**§51: the close has been verifying five views that nothing checked.**
`check_anon_exposure.py` — the script the rules name, and explicitly say not to
hand-roll — does not test `v_event_summary`, `v_kpi_event_financials`,
`v_kpi_parties`, `v_kpi_dance_infusion` or `v_kpi_dashboard`. Its output *reads*
like it does: 54 lines, dozens of objects, one similarly-named view
(`v_kpi_targets_current`) present, and a confident closing sentence.

Prod was fine, and appears always to have been. But a genuine regression would
have produced an identically clean close. This is a step past §37 — there the
check measured a proxy for the invariant; here the ritual was the proxy, because
running a script called `check_anon_exposure` *felt* like checking anon exposure.
`scripts/check_financial_views.py` now asserts it by name.

# Part two — Gear Watch (same day, second close)

**Machine:** desktop. **Migrations:** none. **Commits:** `8cc4bfa`, `8b09b22`.
**Edge functions deployed:** `scan-gear-market` v17, `ebay-account-deletion` v1.

## The arc

Keith asked two questions: were the automated scans working, and why did "Run
scan now" error. The answers turned out to be "half of them" and "it has never
worked, not once".

**The button had a failure mode with no evidence.** 19 runs in the log, all cron,
zero manual — because the run row is written last and every manual press died at
the 150s wall clock before reaching it. Reproduced at 151.3s. A feature can fail
every single time for a week and leave nothing behind but a toast that fades.

**Two of four sources were dark, and they were the good ones.** eBay had never
run. Facebook had run exactly once, on 2026-08-19 — and produced the three
highest-scoring hits the tool has ever made (93, 85, 75). The scanner was working
correctly and looking in half the places.

**Then I spent two rounds accusing Keith's credentials of being wrong.** They
weren't. See below.

## Key decisions

- **Split the button by cost and latency, not category** (§53). Free-and-instant
  and paid-and-blocking cannot share a control.
- **Bound the blocking call, and refuse one you can't finish** — starting a scrape
  that will be killed wastes the credit and the wall clock together.
- **Rotate, and name what was missed.** Only 2–3 Facebook scrapes fit. Starting at
  target #1 every press meant the tail was never searched, ever, while reporting a
  clean scan. `PARTIAL` is now its own state naming the gear, not a count.
- **Deleted the two secrets I had corrupted** rather than leaving them, so the
  scanner said `NOT CONFIGURED` (true) instead of blaming Keith's key for a value
  I put there.
- **Did not author a replacement for the missing migration 203** — a mismatched
  `sha256` would make the drift permanent instead of loud.

## The honest note

**§52 — I told Keith his eBay keys were wrong. Twice. They were fine.**

The Supabase Management API returns a **SHA-256 digest** in a secret's `value`
field. Read back, every secret is 64 hex characters. I described that digest —
"no hyphens, no PRD marker, not an eBay keyset" — as evidence about his
credentials, copied the digests into the real secret names, and then tested *the
digests* against eBay's OAuth endpoint. It answered `invalid_client`, and I read
that as confirmation. I had authenticated with a hash of his password and
reported that his password was wrong.

He said the values were correct twice. Both times the reply was a more confident
description of the digest. The tie-breaker — "what does eBay say when the real
value is used?" — was the one test not being run, and it was unrunnable by me,
because a secret cannot be read.

The actual cause was the one **he** found: eBay disables a production keyset until
Marketplace Account Deletion compliance is in place, and a disabled keyset returns
the same `401 invalid_client` as a bad key.

*Applied the lesson correctly an hour later:* the function-log query showed zero
calls to `ebay-account-deletion`, which would have proved eBay never called it.
The same query with no filter also returned zero, for functions invoked minutes
earlier — the log source is empty on this plan. Reported as "cannot tell" rather
than "never called".

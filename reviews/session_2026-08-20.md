## The arc

Set out to make the event Money tab easier to use. Ended up finding that the ledger was
publicly readable.

Roughly in order:

1. **Payables (177).** Income had accrual states since 161; costs had none, so a DJ booked
   in August and paid in October could only be recorded as absent or as already paid. The
   real work was not the column, it was deciding *which view counts which state* — P&L
   counts all three, cash and capital and the 1099 count only paid.
2. **Reconciliation.** Payables immediately created a way to double-count: the accrual and
   the real charge both land on the event. Filing a charge now asks whether it settles a
   commitment and merges into the accrual, `external_ref` moving first so a re-push cannot
   resurrect the duplicate.
3. **Forecast (178).** Keith asked for money that is not committed yet. The obvious
   implementation — a fourth status — was the wrong one, and that is §35.
4. **Per-event P&L.** Keith called the money list "too hard to read" and asked for the P&L
   format. It is now literally the same table.
5. **The audit (179–183).** Asked for a full ecosystem sweep. Found one dominant pattern
   (§36), fixed the gaps, built a self-running Data Health control center — and found that
   `autolink_data`, which I had shipped an hour earlier, was callable by every radio
   listener.
6. **Events list.** Type / stage / status / public editable inline, state banding,
   multi-select filters.
7. **Recap staging (184).** Keith asked what happens if he links a still-private
   SoundCloud track. Answer: it renders as a dead player, and the editor's own warning
   said otherwise. Fixed the warning by making it true.
8. **The leak (185, 186).** Found while verifying the above with a key that actually worked.

## Key decisions

- **A forecast is not a status.** It lives on `budget_lines`, a table the P&L structurally
  cannot read, rather than as a fourth value in `expenses.status` that twelve views would
  have had to remember to filter. §35.
- **A missing flag means public.** Both for recap videos (184) and throughout — so no
  backfill is needed and nothing goes dark on apply. Same call 175 made for photos.
- **Auto-linking may only do what the data already implies.** Exact name, exact email, or a
  relationship that exists. No fuzzy matching, ever. §36.
- **Automation must leave a receipt.** Every audit sweep and auto-link writes a summary row.
  A nightly job that mutates the actor graph and leaves no record is drift with a schedule.
- **A check that cries wolf is worse than no check.** Three of the audit's checks were
  rewritten before shipping; the new `post_apply` definer check was narrowed three times.

## The honest note

**Every anon verification I reported before ~20:30 was worthless.** `.env` has no
`SUPABASE_ANON_KEY` — it is `SUPABASE_PROD_PUBLISHABLE_KEY` — so my key was empty, and an
empty key returns 401 for everything. I reported "all financial views return anon 401"
three times, confidently, having proved nothing. The invariant did hold; I had not
established that.

It is the same mistake as the two `post_apply` checks that cried wolf in August and the
Bandcamp endpoint that answers 200 with an error body: **testing a proxy for the invariant
instead of the invariant.** `scripts/check_anon_exposure.py` now refuses to run unless the
key demonstrably works, and reads bodies rather than statuses.

Worth saying plainly: the leak was found by accident, while doing something else. It had
been there since 043.

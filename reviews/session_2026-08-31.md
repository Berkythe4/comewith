**Machine:** laptop (`C:\Users\keith\comewith`). **Migration:** `207` (applied to prod).

## The arc

The ask was small and clear: a Linktree-style page, fully customisable without
having to come back to Claude. Two things about it were genuinely underdetermined,
so they were asked rather than guessed — **how many pages** (one, or several
addressed by slug) and **how much theming control**. Keith took several pages and
full custom with presets on top. Both answers changed the schema, so asking was
cheaper than rebuilding.

The rest of the work was mostly deciding what *not* to build twice.

**The editor wanted a live preview, and the obvious build is the wrong one.** A
small renderer inside `dashboard.html` that draws approximately what `links.html`
draws would have worked on day one and drifted by the second change. The planner
already carries exactly that duplicate on purpose (`v_plan_monthly` vs
`planModelMonth`) and pays for it with a permanent "change both" rule — worth it
there, where SQL and the browser cannot share a runtime. Here they can: the preview
is `links.html?preview=1` in an iframe, fed unsaved state over `postMessage`. One
renderer, and the preview cannot lie about the page because it is the page. It also
filters inactive and out-of-window rows before posting, since that is what the
public view does and a preview that shows more than a visitor sees is worse than
none. §59.

**Clicks were already free, but only if the identity is right.** The site's beacon
counts every link click. Attributing those to a link by URL would have been a guess
— the beacon stores a resolved absolute URL, a row may hold a relative path, and an
edited URL would silently inherit the previous one's history. Each rendered link is
stamped `data-track="link:<uuid>"` instead, and `v_link_click_stats` matches on that.

## Follow-up the same day, after Keith clicked it

Four things, one of them a real bug and the most interesting part of the session.

**Link subtitles were never saved.** The "Small line under it" box was rendered
through `linkField()`, which emits `data-lk="item.<id>.subtitle"`. The input
handler routes every `data-lk` through `linksSetPath`, which writes to the **page**
object — so the subtitle landed on `linksState.page["item.<uuid>.subtitle"]`, a key
`saveLinks()` never reads, and vanished with no error at any layer. It read to
Keith as "the line is not coming up underneath", i.e. a rendering fault on the
public page, because the *seeded* links did show theirs — migration 207 inserted
those directly, so they had never been through the editor at all. That mismatch is
what made it look like a display problem rather than a save problem.

The fix is one attribute (`data-li-f="subtitle"`). The more useful change is that
`linksSetPath` now takes a `LINK_PAGE_FIELDS` whitelist and console-warns on
anything else instead of quietly accepting it. `data-lk` accepting any key at all
is what let a per-link field masquerade as a page field; a setter that will store
anything cannot tell a typo from an intention.

**Three smaller ones.** Social glyphs now use `--accent`, so the icons across the
page read as one set rather than two. The share button always copies and says
"Link copied" — no native share sheet, which on a phone hides the page behind an
OS dialog and moves the answer to "did that work?" somewhere else — with an
`execCommand` fallback that reports "Copy failed" rather than claiming success it
cannot confirm. And every page now carries a built-in `comewith.org` pill at the
top: chrome, not an editable row, so it cannot be deleted by accident on the one
page that most needs a way back to the site.

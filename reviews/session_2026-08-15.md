# Session review — 2026-08-15 · Radio discovery audit (desktop)

## What happened

Keith had been building an episode off the Radio panel with the window set to
**8/18 + 4 weeks** and asked, essentially, "prove we're not missing anyone." Read the
pipeline end to end — `pull-ra-market` / `pull-ticketmaster` / `pull-dice` →
`ra_events` + `ra_artists` → the window filter → `sc-match` / `sc-enrich` → producers
and their tracks — then audited it against prod with `db.py`.

## The arc

Set out to confirm coverage. Expected the answer to be "the pool is fine, you just
haven't scanned it yet" — that part was true (677 of 825 in-window artists with a
SoundCloud link had never been read), but it wasn't the interesting finding.

The real one: **the window was filtering on the wrong date.** `ra_artists` keeps one
row per artist holding their *soonest* show, and the filter keyed on it, so anyone
playing just before the start date *and again* inside it fell out. 77 artists, 70 with
a SoundCloud link. Nothing about a shorter list says "77 missing" — which is why it
survived this long. A start date in the future is the worst possible input for that
schema, and that's exactly what Keith had typed.

Pulling that thread turned up two more of the same shape: **DICE** was returning 7
days against a 90-day request (its 160-item detail cap was binding exactly, tag-order,
so weeks 2–4 had *zero* DICE), and **Ticketmaster** was Manhattan-only because its
`city` param is a literal string match. Both failed as empty results, not as errors.
And "↻ Pull shows" was swallowing both sources' failures anyway.

## Decisions

- Windows over artists are evaluated against **`ra_events.lineup`**, not the
  denormalized `next_event_date`. A "next X" column is a summary of the pull, not a
  fact about the entity (LEARNINGS §15).
- Any pull that caps or truncates must **report what it dropped**; the caller surfaces
  it. Silent truncation is the failure mode, not the cap.
- Work stayed on a branch. `master` auto-deploys, and Keith hadn't green-lit a deploy.

## Shipped later the same day

Keith green-lit it: `radio/window-by-lineup` merged (`88b2153`), Netlify published the
dashboard, and `pull-dice` (v5) + `pull-ticketmaster` (v7) went to prod. Financial
views re-verified anon 401 after.

The deploy turned up its own snag worth keeping: **`supabase functions deploy` can't
be used on this repo at all.** CLI 2.101.0 rejects the newer `sbp_v0_…` PAT format
outright ("Invalid access token format") on top of being linked to staging. The
Management API accepts the same token, so deploys now go through
`scripts/deploy_edge_function.py`, which also preserves each function's existing
`verify_jwt` instead of resetting it.

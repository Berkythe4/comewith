# Session 2026-08-27 — radio and artist profiles, linked both ways

**Machine:** desktop. **Migrations:** `204`, `205` (both applied to prod).
**Commits:** `4cc2436`, `6bc3188`, plus 205 and the section reorder.
**Edge functions:** `get-station` v33. **Prod data:** one row —
`actors.public_profile` for 32LVS.

## The arc

Set out to link radio episodes to artist pages. The ask was ambiguous in a way
that mattered — "the artists content page" could mean each track's artist or the
DJ who mixed it — so it got asked rather than guessed. Keith wanted the mixer,
plus the reverse link. Good thing: radio tracklists are external NYC acts with no
`actors` row, so per-track links would have fired on almost nothing and looked
broken.

**The interesting work was not the feature.** Mid-build Keith added: *"a gig
should only show up on the artist page if it is public."* `v_artist_gigs` was
gated on `is_public = true OR status = 'completed'`, and the second half was a
real leak — every completed event published its participant list by name whether
or not it had been announced.

**204 fixed it and was wrong anyway.** Gating on `is_public` alone read
correctly, dry-ran clean, and would have been a quiet regression across nine
public profiles: the pre-apply count showed gigs going 60 → 24, with **Dance
Infusion #1 and #2** among the casualties. `is_public` is the *upcoming-events*
flag — both consumers also filter `event_date >= current_date`, so nobody had
ever set it on a past event because it did nothing. The past-facing flag is
`is_featured`, which drives Recent Rooms.

**205 encodes the rule instead of syncing the flags.** `is_public OR
is_featured` — Keith's answer to "which past events count" was *"everything that
is showing in recent rooms"*, and hand-flipping today's featured events would
have produced the same result this afternoon and drifted the moment he featured
the next one.

## Key decisions

- Link on `mix_by`, the name **printed**, never `assigned_actor_id` — the FK is
  who was given access to *build* the episode, and would point "Mixed by
  \<guest\>" at somebody else's profile. Ambiguous names link nowhere. §55.
- The reverse lookup is a `?artist=` mode on `get-station`, not a new anon view,
  because 103 anon-revoked `sc_playlists` specifically to make station reads
  function-only.
- One helper decides both directions, so they cannot disagree.
- Radio **leads** the profile when an artist has episodes, via markup order and a
  hidden section — no JS reordering.
- Paged the per-station track aggregate by primary key while in there; it was a
  bare select against a silent 1000-row cap (§18).

## Parked / next

- **32LVS is published with an empty profile** — no bio, photo or socials, so
  they render as a placeholder on the homepage collective. Their self-edit link
  fixes it with no deploy. Top of CARRYOVER.
- The **203 drift is untouched and still owed by the laptop.** Next number is 206.
- Per-track artist links: considered, not built. Revisit only if the collective

## One honest note

The pre-apply count is the only reason 204 did not stand as the final answer. The
migration was written, reviewed, dry-run and applied — every gate in CLAUDE.md
passed — and it still would have stripped the flagship shows off nine profiles.
Dry-running proves a migration *runs*. Counting the rows it changes, and reading
their names, is what proves it is **right**. For a view whose entire body is a
`where` clause, that second check is the only one that means anything.

## Addendum — the minutes (migration 206)

Keith came back with two bugs on the new profile cards: "incorrect minutes" and
"invalid date". Both were older and wider than the page he saw them on.

The date was a one-liner — `fmtDate` appending `'T00:00:00'` to a timestamptz.
`radio.html` had already solved it; `artist.html` hadn't inherited the guard.

The minutes were the real one. Every surface summed the source-track lengths,
which is not the runtime of a DJ mix. `sc-connect mix_stats` was already pulling
the published mix's track object for its play count and throwing `duration`
away. Now stored (206), served as `mix_min`, read by all four surfaces, and
backfilled across the 7 live episodes — which also refreshed play counts that had
been stale since July.

**And it produced the session's second correction.** I explained the bug in a
migration comment, a prod column comment and two edge functions before the real
durations existed to check against — and got the direction backwards, asserting
SHOW 6's "43 min" was an under-report when 43 is simply correct. Four of the
seven episodes were within a minute of the truth, which is exactly why nobody
caught the bug for months. LEARNINGS §56: print both numbers per row *before*
writing down why the old one was wrong.

# Session 2026-08-27 (part two) — pricing models: quantity x rate (LAPTOP)

*Work done 2026-08-22; closed 2026-08-27. One build: pricing models.*

## The arc

- **Set out to do:** answer "where should I start", which the docs said was "run
  the anon sweep, but only on the desktop".
- **Discovered immediately:** it was never a desktop-only job. The sweep needed
  `SUPABASE_PROD_PUBLISHABLE_KEY` in `.env`, and that key is **public by design** —
  it ships inside `dashboard.html` because the browser needs it. Added it, ran the
  sweep, 0 FAIL. An item that had been blocking the top of CLAUDE.md and CARRYOVER
  for a week was a one-line config gap, not a machine constraint.
- **Then did the actual ask:** Keith wanted every line to read quantity → amount →
  total ("100 tickets at 25 = 2500", "1 production fee at 500 = 500"), and could
  not find any way to add or remove a line. Migration 203 plus a rewrite of the
  Pricing models surface.

## Key decisions

- **`quantity` is a multiplier that composes with `basis`, not a replacement for
  it.** `per_scale` becomes qty × rate × scale, so "2 drinks a head" is
  expressible and the ordinary qty-1 case still reads as "$25 a head" and stays
  live to the attendance lever. The alternative — making quantity mean the scale —
  would have made the lever dead on exactly the lines it matters for.
- **`pct_revenue` pins quantity to 1 by constraint** rather than ignoring it. A
  field the maths quietly drops is worse than one you cannot fill in wrong.
- **A new line is created empty and flagged**, never pre-filled with a plausible
  category. And the category box is a controlled list built from `v_pl_monthly` +
  `revenue_streams`, because `category` is the join key and free text there is
  exactly how the legacy `budget_lines` rows reported 100% variance in silence.
- **Totals repaint as you type, not on blur.** A total that waits for blur to agree
  with the quantity above it reads as a bug every single time.
- **Two schema-refused options removed from the UI** rather than left to fail at
  save time: "% of revenue" on income lines, and basis-switch without resetting
  quantity.

## The honest note

**None of this has been clicked.** There is no dashboard login on this laptop, so
the entire UI — the qty cells, add, remove, the live totals — is verified only at
the data layer and by parse. That is the second session in a row to hand the
Planning tab over unexercised, and the pile of unclicked surface is getting deeper
rather than shallower. It is the first item in CARRYOVER for a reason.

## What the checks actually caught

- **The dry run caught a real failure the repo could not show.** 203 rebuilt
  `v_plan_offering_unit` from 198's definition, but 199 had replaced that view with
  two extra columns; `create or replace view` cannot drop columns, so the apply
  would have failed outright.
- **The inertness proof was not enough on its own**, and knowing that is the
  session's durable lesson (LEARNINGS §57). A fingerprint showing "nothing moved"
  is equally consistent with "the column is ignored". Needed a perturbation that
  MUST move the number and a violation that MUST be refused.
- **An RLS negative control was found erasing its own evidence** — raising inside a
  plpgsql `BEGIN … EXCEPTION` rolls back the insert it is reporting — and leaking
  the admin's JWT claims into the "anon" block, because `set_config(…, true)` is
  transaction-local, not block-local.

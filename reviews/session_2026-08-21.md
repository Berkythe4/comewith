# Session 2026-08-21 — the content list, and the last public view

**Machine:** desktop. **Migrations:** 187. **LEARNINGS added:** §38, §39.

## What I set out to do

Both items the 2026-08-20 close left at the top of `CARRYOVER.md`:

1. Redo the Social Calendar's **timeline** view as a **list** view, to the same spec
   as the events list.
2. Decide what happens to `tools/visualizer.html` — served publicly with no sign-in,
   reading `v_kpi_targets_current`. Either it gets auth, or the view stays public
   deliberately.

## The arc

**Item 1 went as specified**, with one judgment call and two design problems the spec
could not have anticipated.

The judgment call: the module already had a `list` view — a plain read-only table.
Building the new list "as the timeline" would have left two views called List. The new
one has everything the old one showed plus inline editing, clickable names, banding and
filters, so it **replaced both**. Views are now Calendar / List / Board.

The two design problems were the interesting part, and became §38. The spec said to put
`hub-status-sel ev-inline` selects on "the fields that actually move — stage, scheduled
date, channels, pillar". Two of those four cannot take a select without losing data:
`channels` is an array (a select flattens a two-channel post to one) and
`content_pillar` is free text (a select over a hardcoded list rewrites anything not on
it). Chips-plus-add for the first, derived options for the second.

**Item 2 was not the question it looked like.** The choice offered was auth-vs-public,
but reading `tools/visualizer.html` showed it already loads `/staging/guard.js` and
imports its Supabase client from it — it has had auth all along. And asking prod as the
public showed its other two sources already answer `200 []` and `401`, so the tool never
worked signed-out and the grant was protecting nothing. There was no trade-off to make;
there was a wrong premise, written into 186's header, that nobody had executed. Revoked
in 187. That became §39, which is §37's failure one level up: §37 was two checks testing
a proxy for the invariant, §39 is a decision *not* to check resting on prose that read
as authoritative because it sat in a migration file.

## Decisions

- **The timeline view is deleted, not kept.** The list supersedes it entirely.
- **An inline editor must be able to express every value its column can hold** (§38).
  Where it can't, widen the control or leave the field to the modal.
- **`v_kpi_targets_current` is revoked from anon** (187). `authenticated` keeps SELECT,
  verified before and after, so the visualizer and dashboard are unaffected.
- **The exception moved out of `PUBLIC_OK` and into `MUST_BE_EMPTY`** in
  `check_anon_exposure.py`, so the sweep enforces the new state instead of documenting
  the old one.

## Verification worth noting

- The key-sanity probe in the financial-view check **returned 400 on the first attempt**
  (`v_public_events` has no `id` column), which is precisely the shape §37 warns about —
  a check that isn't really asking. Re-ran with `select=*`: 200 with a real body, and
  the same call with an empty key gives 401. Only then were the five 401s meaningful.
- Three of the 26 new tests were **mutation-tested** — break the pillar editor, the
  banding, the caption search, and each fails as it should. A regex that passes against
  a mutant is documentation, not a test.
- `node --check` on the extracted module, with the **pre-edit version as a control**, so
  an artifact of the extraction couldn't read as a real error.

# Part two — invoicing, built from nothing

**Migrations:** 188–194 (plus 187 above). **LEARNINGS added:** §40, §41, §42.
**Edge functions:** `invoice-doc` v7 (new), `resend-webhook` v22.

## What I set out to do

"Generate invoices from the income and event money tabs, PayPal or wire to
Bluevine, template + storage + create/send/download-PDF, think about the whole
workflow." Then, iteratively: widen it, make it findable, confirm before
sending, add Venmo, add a history.

## The arc

**The accounting shape was the first real decision, and it drove everything
else.** An invoice must not be revenue — the income row already is. Once that is
fixed, `income.status = 'invoiced'` (defined in 161, unreachable ever since)
becomes the thing sending an invoice *does*, partial payments have to live on the
invoice because an income row cannot be half settled, and no view in the whole
feature is allowed to sum into the P&L.

**The PDF was the biggest risk and the most satisfying part.** No library, so a
~280-line writer against the standard-14 fonts. What made it safe to do was that
it could be verified: `pypdf` parses the output, so "does this open" is a test
rather than a hope. Three layout bugs all had the same cause — a height estimate
that guessed instead of measuring what it was about to draw.

**Two implementations of the money is a deliberate cost.** The dashboard reads a
SQL view; the PDF and the client's page read TypeScript. Checking them against
each other on prod inside `BEGIN..ROLLBACK` — same discount, same non-taxable
line, same tax — and getting identical numbers to the cent was the point at which
the feature felt real.

**Keith found three bugs I should have found.** The nav group that did not exist,
so Invoices sat on its own away from Income. The Payment details screen that was
unopenable because I revoked the grant instead of relying on the policy. And the
missing Send button — modal chrome leaking from the invoice editor into every
screen opened after it, which was the *second* time that same leak was reported.
The third one is why §42 is a guard with a mutation test rather than a fix.

**Bluevine turned out to be a research question, not a build question.** Their
invoicing is Stripe underneath with no public API, so it cannot be driven from
the dashboard. Answering that honestly — and saying what the real upgrade path
is — was more useful than either adopting it or dismissing it.

## Decisions

- An invoice is not revenue; totals are computed, never stored (§40).
- Bank details go in their own master-only table, never `site_content`, which is
  anon-readable by design.
- The client-facing page is function-only on the service role, matched on
  `public_token`; drafts and voided invoices 404 to that token.
- Preview opens the real PDF, not a web rendering of it — it cannot diverge from
  what the client receives because it is the same bytes.
- The "Pay online" URL is off the PDF: no reader makes it clickable, so it asked
  a client to retype a UUID.
- Extra payment rails are data, not columns. Delete to stop offering one; a
  disabled row holding a real account handle gets re-enabled by accident.

## Parked / next

Keith must enter the payment details before any invoice can actually be paid —

wire rail on but no account number filled in, which is worth a look. After that,
the Bluevine reconciliation loop is the obvious next build.

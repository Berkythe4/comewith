# Session 2026-10-29 (desktop): Event Control Center, DI #3 first

**What happened**

  it", so the Phase 1 approval stop was skipped.
- Shipped 222 (schema) and 223 (DI #3 seed) to prod. Both were dry-run first, and every
  check passed.
- Built `control.html` and `assets/control-center.js`, with 49 tests that include the real
  DI #2 exports. The page links from the event hub, and is live on Netlify.
- Tested it in headless Chrome against an in-memory copy of the prod rows. All 8 sections
  passed at 1280px and 380px, as did the imports, check-in and the exec save, with 0 errors.

**The arc.** We set out to build eight screens. We found that most of the data model
already existed:
- the door list is `guest_event_attendance`;
- blockers are tasks with status `blocked`;
- planned costs are `budget_lines` in the forecast column.

So the job became mostly reuse. The real DI #2 files exposed two traps, and neither
would have errored:
- **Zeffy sells sponsorships through the ticket form.** Imported as tickets, sponsor
  cash would have been counted twice (§99).
- **DI #1's aggregate RA rows have no key to match on.** A per-barcode re-import would
  have doubled its revenue (§100).

**Decisions**
- A standalone page, not a dashboard tab: the door runs on phones, and the dashboard is 1.3 MB.
- The production share of a tier is derived, never stored. Drink tickets count once
  (the larger of package and handed out).
- A ticket with no tier is held back until it is mapped. Past events take attendance only.
- "TBD" is a boolean next to a NOT NULL number, so four money views are left untouched (§101).
- The win-back flow only tags a segment for Campaigns. It never subscribes anyone.

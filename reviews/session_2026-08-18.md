# Session — 2026-08-18 · Gear Watch, and the paperwork behind it (DESKTOP)

## What happened

Keith's DJ rig (~$15K) was stolen out of a vehicle parked on his block overnight. NYPD is
running it as grand larceny with a detective and an evidence team. The session produced
two things: the document the case runs on, and an automated watch for the resale market.

- **`Financial/ComeWith_Stolen_Gear_Loss.xlsx`** — one file for three readers: the
  detective (serials for NCIC / LeadsOnline), the DA (restitution), the insurer. Built
  from `ComeWith_Work_Expenses_Master.xlsx` → *Equipment (Capital)*, reconciled twice
  against Keith's own list, final roster **10 units / $11,713.07** documented.
- **Gear Watch** — migration `146`, edge function `scan-gear-market`, a tested confidence
  model, a master-only dashboard panel, and a runbook. Scans 3×/day; alerts by email,
  panel and push. **Held in the working tree — not applied, not deployed, not pushed.**

## The arc — what I set out to do vs. what I found

**Set out to** build the spreadsheet from the equipment list on the website. **Found** the
website list is a *rental* page: models and day rates, no serials, no prices. The real
source was the financial master, and the Simplifi export located the actual purchases.

**Set out to** treat the sheet's `D002` / `S001` codes as serial numbers, since the column
is literally called "Serial #". **Found** they are internal asset tags. Police cannot put
an asset tag into NCIC, so every Serial # cell ships reading `NEEDED` rather than
pre-filled with something that looks complete and is useless.

**Set out to** scan four sites. **Concluded**, from a real 403, that Craigslist was
impossible. **Was wrong** — Keith said his brother had built a Craigslist puller and
pushed back. He was right: the RSS path is genuinely dead, but the site's own search box
calls an internal JSON endpoint that answers 200, which is the same technique CLAUDE.md
already documents for Bandcamp and which I hadn't tried before writing the obituary.
Craigslist is now the only source verified working end to end. OfferUp and Facebook
Marketplace remain genuinely unautomatable.

**Set out to** ship the scanner once the tests passed. **Found four bugs by running it
against live data**, none of them visible from the code: a defaulted location that handed
out-of-area listings the local bonus; a geo string carrying *two* indexes into two arrays,
which put a Schenectady listing in Bushwick; substring geo matching, so `"ny"` matched
**albany**; and a zero-result payload (`decode: 0`) that was being reported as FAILED —
the exact mistake §24 was written to prevent, pointed the other way.

## Key decisions

- **LEARNINGS §24** — "blocked" and "nothing found" are different answers. A dead source
  is reported FAILED per-source, never folded into the total.
- **LEARNINGS §27** — and "I couldn't reach it" is not "it can't be reached". §24's
  reasoning was sound; the conclusion it drew about Craigslist was not. When one access
  path fails, open the site's own network tab before declaring the source impossible —
  and when the user says "I know this works", treat that as evidence of a path not tried.
- **LEARNINGS §25** — pg_cron calls edge functions with a service-role bearer read from
  vault at call time. Closes the auth question `014_cron.sql` deferred in Phase 10, and is
  now a standing rule in CLAUDE.md.
- **LEARNINGS §26** — never default a field that feeds a score. A placeholder that flows
  into a computation becomes invented evidence.
- **Cases and stands are not scan targets.** No serials, low value, and "CDJ case" matches
  thousands of listings. They stay on the loss schedule; they are not worth hunting.
- **Scores are never shown bare.** Every hit carries its breakdown, because "87/100" is
  not something you can hand a detective.
